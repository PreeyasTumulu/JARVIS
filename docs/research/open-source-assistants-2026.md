# Borrow their pipelines, keep JARVIS's gate

> Research for Phase 23, 2026-11-05. Five research passes over primary sources (repos, docs, release pages, issue trackers), then a synthesis. Four claims that Phase 24 builds on were re-checked by hand against the primary source: Home Assistant's `processed_locally` on `intent-end`, Open WebUI's experimental and off-by-default tool approval and its ~30B note, Pipecat's `cancel_on_interruption` and related options, and LiveKit's agent and user states. Release years marked inferred come from pages that print only day and month. The summary and Jarvis's decisions are in [RESEARCH.md](../RESEARCH.md) section 6.

The leading open-source assistants agree on architecture and disagree on safety. Nearly all of them route common commands through a deterministic path before any LLM sees them. Examples are Home Assistant's "prefer handling commands locally", OpenVoiceOS's tiered intent pipeline, Leon's controlled mode and isair/jarvis's separate fast router model. They also stream LLM tokens into sentence-chunked TTS and expose tools through MCP and `SKILL.md`-style files. Almost none of them enforces per-action confirmation in code. Open WebUI's approval switch is experimental and off by default, classic Open Interpreter's safe mode defaults to off, Windows-MCP calls its permission rules "tool-use guidelines, not server-enforced approval", and OpenClaw runs tools on the host unless the user sets up sandboxing ([Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/); [SAFE_MODE.md](https://github.com/endolith/open-interpreter/blob/main/docs/SAFE_MODE.md); [Windows-MCP README](https://github.com/CursorTouch/Windows-MCP); [OpenClaw README](https://github.com/openclaw/openclaw)). That makes JARVIS's typed risk floors, privacy labels, code-enforced policy gate and audit log its clearest advantage, and nothing in these projects argues for weakening them. The patterns worth borrowing are specific:

- Leon's staged loading of tool schemas and its runtime argument guards.
- Home Assistant's worst-case tool annotations, its `processed_locally` flag, and one transcript shared between the fast path and the LLM.
- Pipecat's `cancel_on_interruption` and its bundled Smart Turn model.
- LiveKit's five agent states and its recovery from false interruptions.
- Open WebUI's memory types with character budgets.

Model size limits every recommendation. Open WebUI's docs, a 2026 Open Interpreter review and Home Assistant users all report that small local models produce malformed or unreliable tool calls. The floors they give are roughly 30B, 14B and 7B respectively ([Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/); [DEV Community review 2026](https://dev.to/jovan_chan_9500711396d4e6/open-interpreter-review-2026-code-interpreter-offline-4g80); [HA community thread](https://community.home-assistant.io/t/help-local-ai-voice-assistant-intent-error/860489)). So Hermes 3 8B needs three things: a short tool list on each turn, deterministic routing first, and validation in code. Latency evidence points the same way. Streaming TTS cut Home Assistant's time to first audio from 5.31 s to 0.56 s ([HA blog, 2025-09-11](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)). Fully local voice-to-voice under about 1.2 s has only been shown on Apple Silicon, or in anecdotal reports from 8B stacks.

## The field in November 2026: two giant platforms, two voice frameworks, several reference designs

The landscape changed shape during 2026. **OpenClaw (393,924 stars) and Hermes Agent (260,601 stars) are an order of magnitude larger than anything else.** Both are general personal-agent platforms that live in chat apps such as WhatsApp. Neither is voice-first ([GitHub API repo query](https://api.github.com/search/repositories?q=repo:microsoft/UFO+repo:openclaw/openclaw+repo:leon-ai/leon+repo:OpenInterpreter/open-interpreter+repo:PanPenek/JarvisAi+repo:CursorTouch/Windows-Use+repo:NousResearch/hermes-agent+repo:isair/jarvis+repo:Priler/jarvis)). Several familiar names now mean something different:

- **Open Interpreter** is now a Rust fork of OpenAI Codex under Apache-2.0. The classic Python code-execution design survives only in a community fork under AGPL-3.0 ([OI README](https://github.com/openinterpreter/open-interpreter); [endolith fork README](https://github.com/endolith/open-interpreter)).
- **Leon** is in the middle of a rewrite. The agentic 2.0 Developer Preview lives on `develop`, and no 2.0 release has shipped ([leon-ai/leon README](https://github.com/leon-ai/leon)).
- **Willow** is in low-energy maintenance by essentially one maintainer. Its inference server dropped LLM support on 2026-02-12 ([GitHub API, Willow commits](https://api.github.com/repos/HeyWillow/willow/commits); [GitHub API, WIS commits](https://api.github.com/repos/toverainc/willow-inference-server/commits)).

## Deterministic routing first is the one architecture everyone converged on

**Every mature voice project now puts a deterministic matcher in front of the LLM**, and they give the same reason JARVIS would. Home Assistant introduced "Prefer handling commands locally" because "many easy-to-run commands were being sent to an LLM, which can slow down things and waste tokens" ([HA Voice chapter 9, 2025-02-13](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)). By September 2025 it was the default: only commands the built-in agent cannot understand reach the AI ([HA blog, 2025-09-11](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)). The matcher compares text against hassil sentence templates such as "turn on the {name}". An English-only fuzzy matcher, added in 2025.9, absorbs extra words that used to produce "the dreaded 'Sorry, I couldn't understand that'" ([HA Voice chapter 11, 2025-10-22](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)). The default agent also keeps a 128-entry LRU `IntentCache` so repeated phrases skip re-matching (dev branch) ([default_agent.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/conversation/default_agent.py)).

OpenVoiceOS takes the idea further with an explicitly **ordered, confidence-tiered pipeline** set in `intents.pipeline`. The documented order is `ovos-m2v-pipeline-high`, `ocp_high`, `stop_high`, `converse`, `padatious_high`, `adapt_high`, then medium tiers, `common_qa`, `fallback_medium` and `fallback_low`. In this design LLM "personas" act only as an active conversation or as a catch-all fallback ([OVOS pipelines overview](https://openvoiceos.github.io/ovos-technical-manual/pipelines_overview/); [OVOS personas](https://openvoiceos.github.io/ovos-technical-manual/150-personas/)). ovos-core 3.7.0a1 "bounded each pipeline match call and gave each plugin its own workers". The notes read this as a sign that slow matchers caused hangs. Note that GitHub shows that release as "18 Sep" with no year ([ovos-core releases](https://github.com/OpenVoiceOS/ovos-core/releases)). The same pattern shows up elsewhere:

- **Leon 2.0** offers `agent`, `smart` and `controlled` (deterministic native skills) modes ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md)).
- **isair/jarvis** runs a separate fast model for voice intent detection and tool routing, distinct from the chat model ([isair README](https://github.com/isair/jarvis)).
- **Pipecat** added `LLMWithBackend` (alpha) in v1.13.0: a fast frontend LLM hands deeper work to a backend LLM through a `delegate` tool. v1.15.0 added "predictive delegation", where a classifier starts the backend early ([pipecat releases](https://github.com/pipecat-ai/pipecat/releases)).
- **Open WebUI's** Realtime voice calls hand "real questions" to the chat's selected model and tools ([Open WebUI releases](https://github.com/open-webui/open-webui/releases)).

The most important structural lesson comes from Home Assistant: **the fast path and the LLM share one executor and one transcript.** Intents become LLM tools through `llm.IntentTool`, so permissions are enforced in one place. Since early 2025 "the conversation history is shared with the LLM", so "Add milk to my shopping list" handled locally can be followed by "Add rice" handled by the AI ([HA contributors docs, LLM API](https://contributors.home-assistant.io/core/internals/llm-api/); [HA Voice chapter 9](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/); [HA blog, 2025-09-11](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)). Each pipeline's `intent-end` event carries a `processed_locally` flag that records which path handled the turn ([HA developer docs, voice pipelines](https://contributors.home-assistant.io/core/internals/assist-pipelines/)). Willow is the counterexample. Its MultiNet local mode compiles a fixed grammar at build time: at most 400 commands, a 63-character limit, numbers spelled as words, English only. It calls itself "beta (in a project that is beta)" ([Willow Local Command Support](https://heywillow.io/features/Local-Command-Support/)). Matching templates at runtime is the better model for JARVIS's exact-phrase fast path.

For the agent loop itself, **none of the strong projects is built on LangGraph.** They run custom loops ([OpenClaw README](https://github.com/openclaw/openclaw); [Hermes README](https://github.com/NousResearch/hermes-agent)). The nearest analogue to a LangGraph state graph is Microsoft UFO2. Its HostAgent is a 7-state finite-state machine and its AppAgent a 6-state one, coordinated through a Blackboard over a four-phase cycle: data collection, LLM interaction, action execution and memory update. UFO2 also predicts several actions per LLM call and validates them against UI state, claiming "51% fewer queries". That figure is a project claim and was not checked independently ([UFO2 overview](https://microsoft.github.io/UFO/ufo2/overview)). Leon's turn lifecycle is the most explicit about where checks run. The model requests tools, and "runtime guards validate and repair arguments and block duplicates before execution". Memory extraction, titles and self-model updates then run asynchronously after the turn, and a completion review checks evidence ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md)). Step caps are common: LiveKit 1.8.6 enforces `max_tool_steps`, and PanPenek/JarvisAi allows "up to 15 sequential tool calls per request" ([livekit/agents releases](https://github.com/livekit/agents/releases); [PanPenek README](https://github.com/PanPenek/JarvisAi)).

The voice frameworks split along a clear line. **Pipecat is a lower-level pipeline of frame processors with a `LocalAudioTransport` and no required server.** LiveKit Agents is a higher-level `AgentServer`/`AgentSession`/`Agent` framework built around WebRTC rooms ([pipecat repo README](https://github.com/pipecat-ai/pipecat); [livekit/agents README](https://github.com/livekit/agents)). LiveKit's `console` mode runs local audio, but the docs frame it as "Local, single-session, terminal-based testing", and LiveKit Inference still needs credentials ([LiveKit docs, Agent Console](https://docs.livekit.io/agents/start/console)). Neither framework documents Windows as supported. One community user had to pass `PipelineRunner(handle_sigint=False)` to work around a Windows signal-handler error ([Asterisk community thread](https://community.asterisk.org/t/connecting-asterisk-with-pipecat/109856)). Both change fast and break things: Pipecat shipped v1.13.0 to v1.15.0 in ten days, with breaking dependency changes along the way ([pipecat releases](https://github.com/pipecat-ai/pipecat/releases)). Borrowing their designs and small components is safer than embedding either framework.

## MCP and skill files became the plugin standard, but permission manifests did not

**MCP is now the common extension point** across Hermes Agent ("Any MCP server can be connected"), UFO2 and UFO3 Galaxy, isair/jarvis, ethanplusai/jarvis, Pipecat, LiveKit ("one line of code", Python only), Home Assistant and Open WebUI ([Hermes README](https://github.com/NousResearch/hermes-agent); [UFO README](https://github.com/microsoft/UFO); [isair README](https://github.com/isair/jarvis); [LiveKit docs, tools](https://docs.livekit.io/agents/build/tools/); [HA MCP Server docs](https://www.home-assistant.io/integrations/mcp_server/)). Skill files are the second standard. Hermes is compatible with agentskills.io. Leon loads `SKILL.md` agent skills on demand and stores LLM-learned "experiences" as `SKILL.md` files, capped at 196 per profile and retained by last use ([Hermes README](https://github.com/NousResearch/hermes-agent); [Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md)). OpenClaw stands apart: it routes new capabilities through its own plugin SDK and ClawHub, and its README does not mention MCP ([OpenClaw README](https://github.com/openclaw/openclaw)).

The most useful plugin ideas address one problem: how to keep the tool list short enough for a small model.

- **Leon loads tool schemas in stages** from a toolkit catalog: first the toolkit, then the tool, then the function. Its computer-use tools are "progressively loaded" so unrelated turns never see them ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md); [leon-ai/leon README](https://github.com/leon-ai/leon)).
- **Open WebUI's** experimental `ENABLE_TOOL_SEARCH` keeps large tool definitions out of each request until the model searches for them. v0.12.2 added a `call_tool` helper, and v0.12.4 made skills load on demand to cut per-message overhead ([Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/); [Open WebUI releases](https://github.com/open-webui/open-webui/releases)).
- **Home Assistant** builds tools for each request through `async_get_tools(hass, llm_context, api_id)`. It reads state through a `GetLiveContext` tool instead of dumping every entity into the prompt ([HA LLM API docs](https://contributors.home-assistant.io/core/internals/llm-api/); [homeassistant/llm.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/homeassistant/llm.py)).

Home Assistant users show why this matters. CPU-only Ollama hangs once Assist tools are enabled, which users blame on context overflow from loading the whole home ([HA community thread](https://community.home-assistant.io/t/local-ollama-and-assist-hangs/966630)).

Home Assistant also has the best tool metadata in the field. **`llm.ToolAnnotations` mirror MCP annotations and default to the worst case**: `read_only=False`, `destructive=True`, `idempotent=False`, `open_world=True`, because "the defaults assume the worst, so declare what is true for your tool". Tool names must carry a `domain__name` prefix, and unprefixed names "stop working in Home Assistant 2027.3" ([HA LLM API docs](https://contributors.home-assistant.io/core/internals/llm-api/)). Leon separates three tool states: installed (in the registry), enabled (not disabled by the owner) and available (required settings present) ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md)). Pipecat's "direct functions" derive the schema from a typed signature and docstring. Its `MCPClient` gained a `tools_arguments` option to "pin arguments the model can't set" ([Pipecat function calling](https://docs.pipecat.ai/guides/learn/function-calling); [pipecat releases](https://github.com/pipecat-ai/pipecat/releases)).

Pipecat and LiveKit lead on long-running tools. In Pipecat, **`cancel_on_interruption` defaults to `True`**, which makes the call synchronous. Setting it to `False` makes the call asynchronous so the conversation continues. Pipecat also offers:

- `timeout_secs`, which cancels the call when it runs out and tells the user the call did not complete;
- `is_final=False`, which streams intermediate updates;
- `cancellable_by_llm=True`, which adds a `cancel_<name>` tool;
- `TTSSpeakFrame`, which lets the assistant speak while a tool runs.

LiveKit's background tools report silent progress (1.8.9). Tools still running at the interruption timeout continue asynchronously, and MCP servers are told when a call is cancelled (1.8.7) ([Pipecat function calling](https://docs.pipecat.ai/guides/learn/function-calling); [livekit/agents releases](https://github.com/livekit/agents/releases)).

Plugin isolation is weak almost everywhere. Open WebUI's Tools, Functions, Pipes, Filters and Pipelines "execute arbitrary Python code on your server". Its RBAC guidance, as summarized by search, says Tools Access should be treated as root-equivalent ([Open WebUI plugin overview](https://docs.openwebui.com/features/extensibility/plugin/); [Open WebUI RBAC permissions](https://docs.openwebui.com/features/authentication-access/rbac/permissions/)). OpenVoiceOS skills are pip packages loaded into ovos-core. By default they share one bus connection, which "malicious or poorly designed skills could exploit" ([OVOS bus service](https://openvoiceos.github.io/ovos-technical-manual/100-bus_service/)). Leon runs tool calls "in isolated workers by default", but whether those workers are OS-level sandboxes is not stated ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md)). **No surveyed project ships a per-tool permission manifest comparable to JARVIS's risk floor plus sensitivity label.**

For Windows desktop control, the strong designs read the accessibility tree first and fall back to vision. UFO2 combines Windows UI Automation with OmniParser visual grounding. It prefers "Native APIs" such as xlwings, win32com and python-pptx, with clicks and typing as the fallback ([UFO2 overview](https://microsoft.github.io/UFO/ufo2/overview)). Windows-MCP uses the accessibility tree and "doesn't rely on any traditional computer vision techniques". It takes 0.2 to 0.5 s between actions, and it exposes Registry, PowerShell and Process tools with "full system access" ([Windows-MCP README](https://github.com/CursorTouch/Windows-MCP)). If JARVIS mounted Windows-MCP through its MCP client, those tools would bypass JARVIS's risk floors unless the gate wraps every MCP tool individually.

## Confirmation is opt-in or missing across the field, and the incidents show the cost

**Code-enforced per-action confirmation is rare, and where it exists it is off by default.** Some examples:

- **Open WebUI's** `ENABLE_TOOL_PERMISSIONS` is experimental and off by default. "Full access" runs tool calls immediately, and "Ask for approval" pauses each call with Allow and Deny. Automations and channel replies always run with full access. In temporary chats, an approval left unanswered for 120 seconds counts as a denial ([Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/)). The new MCP Apps in v0.13.0 (03 Nov, year inferred 2026) are stricter: each tool call an app makes waits for user confirmation ([Open WebUI releases](https://github.com/open-webui/open-webui/releases)).
- **Classic Open Interpreter's** `safe_mode` defaults to `off` and "does not provide any guarantees of safety or security". The Rust rewrite instead runs commands in a native sandbox on macOS, Linux and Windows, and "asks before it escalates beyond the current sandbox" ([SAFE_MODE.md](https://github.com/endolith/open-interpreter/blob/main/docs/SAFE_MODE.md); [OI docs, terminal](https://www.openinterpreter.com/docs/terminal)).
- **Pipecat and LiveKit** document no built-in human-in-the-loop primitive. Confirmation has to be built as a tool flow ([Pipecat function calling](https://docs.pipecat.ai/guides/learn/function-calling); [LiveKit docs, tools](https://docs.livekit.io/agents/build/tools/)).

Home Assistant's safety boundary is **visibility rather than confirmation**: entities must be exposed to Assist "to avoid that sensitive devices, such as locks and garage doors, can inadvertently be controlled by voice" ([HA exposing entities](https://www.home-assistant.io/voice_control/voice_remote_expose_devices/)). In dev-branch code, `lock` and `alarm_control_panel` are not exposed by default. Covers and switches are, with no device-class filter on covers ([exposed_entities.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/homeassistant/exposed_entities.py)). A third-party agent project found that a default-exposed switch let "turn on garage relay" open a garage door by voice ([home-generative-agent PR 901](https://github.com/goruck/home-generative-agent/pull/901)). The notes found no official setting that requires a PIN or spoken confirmation before Assist unlocks a lock, although absence is not proven. Confirmation exists only as automation patterns such as the 2025 "Ask Question" action. Delayed voice commands "cannot be canceled or modified" ([HA Voice chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/); [HA Voice chapter 7](https://www.home-assistant.io/blog/2024/06/26/voice-chapter-7/)). Home Assistant added an "Action history" tab only in 2026.11. It lists each action, its targets, what caused it and when ([HA 2026.11 release notes](https://www.home-assistant.io/blog/2026/11/04/release-202611/)).

The JARVIS-style repos are weaker still:

- **OpenClaw** pairs unknown direct-message senders by default but runs tools on the host for the main session "unless you configure sandboxing". Its security model assumes "one trusted boundary per gateway" ([OpenClaw README](https://github.com/openclaw/openclaw); [OpenClaw security docs](https://docs.openclaw.ai/gateway/security)). Hacker News titles show the result: "OpenClaw privilege escalation vulnerability" (514 points, 2026-04-03), "Top downloaded skill in ClawHub contains malware" (334 points, 2026-02-05) and "OpenClaw is a security nightmare dressed up as a daydream" (397 points, 2026-03-22). Only the titles were read ([HN 47628608](https://news.ycombinator.com/item?id=47628608); [HN 46898615](https://news.ycombinator.com/item?id=46898615); [HN 47479962](https://news.ycombinator.com/item?id=47479962)).
- **Windows-MCP** describes user takeover as "best-effort, not a security boundary" and ships with anonymous telemetry on by default ([Windows-MCP README](https://github.com/CursorTouch/Windows-MCP)).
- **isair/jarvis** describes no per-action confirmation. Community PRs in April 2026 proposed approval gating, a policy engine and an SQLite audit trail (#131 to #133), and all were closed. The notes did not verify whether any was merged ([isair/jarvis issues API](https://api.github.com/repos/isair/jarvis/issues?state=all&per_page=40&sort=comments)).

A few designs do have real, cheap ideas. **ethanplusai/jarvis treats content from web pages, files, other sessions and MCP servers as untrusted. After it reads such content, it refuses acting tools for the rest of that turn.** The README admits this "stops action, not persuasion", and the same project spawns Claude Code with `--dangerously-skip-permissions` by default ([ethanplusai README](https://github.com/ethanplusai/jarvis)). UFO2 runs the agent in a Picture-in-Picture nested desktop through Remote Desktop loopback, so agent and user "don't compete for mouse/keyboard" ([UFO2 overview](https://microsoft.github.io/UFO/ufo2/overview)). A third-party walkthrough shows UFO flagging an email send as sensitive and asking for confirmation, but the UFO README itself does not document the mechanism ([Impress Watch](https://internet.watch.impress.co.jp/docs/column/shimizu/1570581.html)). OpenVoiceOS tells users to keep the bus on 127.0.0.1 and "Never expose the messagebus to the public internet". In September 2026 it added speaker verification that lets only enrolled voices past the wake gate ([OVOS bus service](https://openvoiceos.github.io/ovos-technical-manual/100-bus_service/); [OVOS blog archive](https://blog.openvoiceos.org/archive)).

Open WebUI's advisory stream is the clearest lesson in what happens when tools run inside the server process. The primary GitHub advisory list holds ten advisories from 9 September to 18 October 2026 alone. Among them are session-token theft by any website through the community stats message handler (GHSA-vpq8-f445-hcq7, High) and deactivated users keeping terminal command execution (GHSA-6g45-8g27-fh8q) ([Open WebUI advisories](https://github.com/open-webui/open-webui/security/advisories)). Two older CVEs carry design lessons. Their scores come from aggregators, not NVD, and should be verified before anyone relies on them:

- **CVE-2026-45395.** Before 0.9.5, the tool update endpoint lacked the `workspace.tools` check that the create endpoint had, so denied users could replace tool Python and run it through `exec()`. Its severity is disputed: CVSS v2 9.0 at PT Security against v3 7.2 at exploit-intel ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-45395/); [PT Security](https://dbugs.ptsecurity.com/vulnerability/PT-2026-41190); [exploit-intel](https://exploit-intel.com/vuln/CVE-2026-45395)).
- **CVE-2025-64496** (CVSS 8.0 per aggregators). A malicious model server could send SSE "execute" events that ran JavaScript in the victim's browser. Aggregators disagree on the affected range ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-64496/); [Vulert](https://vulert.com/vuln-db/CVE-2025-64496)).

The lessons for JARVIS are direct: check permissions at every mutating entry point, not only the first, and never let model or MCP output carry an action the gate has not classified.

## Memory that users can read beats memory they cannot

Long-term memory falls into four patterns: plain editable files, full-text search over past sessions, a knowledge graph with a diary, and a vector database. **The bigger projects favour memory the user can inspect.** ethanplusai/jarvis keeps a folder of Markdown files, one fact per file, plus an index the model always sees ([ethanplusai README](https://github.com/ethanplusai/jarvis)). Hermes Agent curates its own memory with periodic prompts to save information, and it searches past sessions with FTS5 plus LLM summaries ([Hermes README](https://github.com/NousResearch/hermes-agent)). isair/jarvis has a diary and a knowledge graph browsable in a Memory Viewer, and it redacts sensitive information "before model context and saved diary entries" ([isair README](https://github.com/isair/jarvis)). Of the surveyed projects, only PanPenek/JarvisAi, a 3-commit repo, uses ChromaDB. That is the store JARVIS plans to adopt ([PanPenek README](https://github.com/PanPenek/JarvisAi)).

Open WebUI's memory system has the most precise schema:

- Memories are per user and stored in the local database.
- They come in two types, `user` and `context`, each with its own character budget (`MEMORIES_USER_CHAR_LIMIT` and `MEMORIES_CONTEXT_CHAR_LIMIT`, default 2000 each).
- They are managed through eight model tools, from `add_memory` to `read_memory_path`.
- `ENABLE_MEMORY_SYSTEM_CONTEXT` can turn off injection on every turn while the search tools keep working.
- An optional background review runs every 10 turns.

The docs warn that very small models handle memory poorly ([Open WebUI Memory docs](https://docs.openwebui.com/features/chat-conversations/memory/)). Leon 2.0 has the richest layered design. It keeps temporary context in a profile-local SQLite store, persistent, daily and discussion memory, hybrid full-text and vector retrieval, and a curated `OWNER.md` with a derived `.owner-profile.json`. Memory extraction runs asynchronously after the turn ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md)). Leon's context files also include browser and activity data. Under JARVIS's rules, that kind of data must never reach a cloud model.

Short-term context has two lessons. Home Assistant shares one chat log between the fast path and the LLM, and keeps 20 history messages by default for Ollama (dev branch) ([ollama/const.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/ollama/const.py)). LiveKit 1.8.6 stores "only the spoken part of a reply" when TTS fails, so after an interruption the context holds what the user actually heard ([livekit/agents releases](https://github.com/livekit/agents/releases)). Neither Pipecat nor LiveKit documents built-in long-term memory.

## Streaming speech and explicit states, not the model, set perceived latency

**The biggest measured latency win in the notes is streaming TTS.** Home Assistant asked Ollama gemma3:4b on an RTX 3090, with Piper on an i5, to tell a long story. Piper's time to first audio fell from 5.31 s without streaming to 0.56 s with it, and cloud TTS fell from 6.62 s to 0.51 s ([HA blog, 2025-09-11](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)). Open WebUI's TTS likewise reads responses sentence by sentence as they stream, and its voice mode has its own system prompt for short spoken replies ([Open WebUI voice and audio docs](https://docs.openwebui.com/ecosystem/computer/ai/voice-and-audio)).

Published end-to-end figures from comparable stacks:

| Setup | Voice-to-voice | Source quality |
|---|---|---|
| M-series Mac, MLX Whisper, Gemma3n 4B, Kokoro, smart-turn v2 | under 800 ms | Maintainer example ([kwindla/macos-local-voice-agents](https://github.com/kwindla/macos-local-voice-agents)) |
| Open models on Modal cloud GPUs with Pipecat | about 1 s | Vendor blog ([Modal via plushcap](https://www.plushcap.com/content/modal/blog/modal-one-second-voice-to-voice-latency-with-modal-pipecat-and-open-models)) |
| faster-whisper, Qwen3 8B on Ollama, Kokoro, Silero VAD | about 1.2 s | Anecdotal Reddit ([snapshot 2026-04-03](https://reddit.sentinel-team.org/posts/1s63wpc/snapshots/2026-04-03T21%3A20%3A24.375333Z)) |
| Willow device plus GPU WIS, end of speech to action | 500 ms or less | Vendor claim, page from 2023 ([heywillow.io](https://heywillow.io/)) |

Stage-level numbers fill in the picture. Willow's inference server transcribes a 3.84 s utterance with Whisper medium (beam 1) in 140 ms on an RTX 3090, 424 ms on a GTX 1070 and 588 ms on a GTX 1060. The team considers medium beam 1 the minimum configuration and says CPUs cannot meet their targets ([WIS README](https://github.com/toverainc/willow-inference-server)). Turn detection is now cheap. Daily's launch post, a vendor source, puts Pipecat's Smart Turn v3 at 12.6 ms on an AWS c7a.2xlarge CPU, against 450.6 ms for v2. It ships as ONNX with weights bundled in Pipecat and became the default stop strategy ([Daily blog, Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/); [Pipecat smart-turn overview](https://docs.pipecat.ai/server/utilities/turn-detection/smart-turn-overview)). Other tuning defaults:

- Pipecat's Silero VAD defaults `stop_secs` to 0.2 ([Pipecat speech input guide](https://docs.pipecat.ai/pipecat/learn/speech-input.md)).
- LiveKit lowers `min_delay` from 0.5 s to 0.3 s and `max_delay` from 3.0 s to 2.5 s when its audio turn detector is used ([LiveKit docs, turn detector](https://docs.livekit.io/agents/build/turns/turn-detector/)).
- Pipecat v1.9.0 added `LatencyBreakdown.contributions`, which splits the user-to-bot interval into VAD silence, turn completion, LLM inference and TTS ([pipecat releases](https://github.com/pipecat-ai/pipecat/releases)).
- Home Assistant's Ollama integration keeps the model loaded with `keep_alive` -1 and leaves "think" off by default ([HA Ollama integration](https://www.home-assistant.io/integrations/ollama/)).

**Barge-in on laptop speakers is still unsolved locally.** Neither Pipecat nor LiveKit documents built-in acoustic echo cancellation for a local speaker setup ([LiveKit docs, turns](https://docs.livekit.io/agents/build/turns/)). One developer found that Pipecat's STT mute filter stopped echo but also discarded real user speech ([Hackernoon](https://hackernoon.com/stop-muting-your-users-building-a-pragmatic-interruption-state-machine-for-voice-ai)). One OpenAI Realtime user fixed speakerphone self-interruption by making the greeting non-interruptible ([OpenAI community thread](https://community.openai.com/t/realtime-api-echo-issue-when-on-speaker-phone/1370092)). LiveKit provides the recovery tools:

- `allow_interruptions=False` on individual utterances;
- `min_duration` and `min_words` thresholds;
- `false_interruption_timeout` with `resume_false_interruption`;
- an adaptive mode that filters backchannels, which is the default only on LiveKit Cloud and in dev mode.

Pipecat added a per-frame `interruptible` flag in v1.12.0 ([LiveKit docs, turns](https://docs.livekit.io/agents/build/turns/); [pipecat releases](https://github.com/pipecat-ai/pipecat/releases)). Home Assistant's Voice PE solves echo in hardware, with an XMOS processor for echo cancellation ([Voice PE launch](https://www.home-assistant.io/blog/2024/12/19/voice-preview-edition-the-era-of-open-voice/)). A laptop has no equivalent.

For UI states, **LiveKit has the cleanest vocabulary.** Agent states are `initializing`, `idle`, `listening`, `thinking` and `speaking`, published as the `lk.agent.state` attribute. User states are `speaking`, `listening` and `away` (15 s by default). Events such as `agent_false_interruption` and `overlapping_speech` sit alongside them ([LiveKit docs, events](https://docs.livekit.io/agents/build/events/)). Home Assistant's pipeline events are finer-grained: `wake_word-end`, `stt-vad-start`, `stt-vad-end`, `intent-progress` and `tts-start`. They carry typed error codes such as `stt-no-text-recognized` ([HA developer docs, voice pipelines](https://contributors.home-assistant.io/core/internals/assist-pipelines/)). Smaller feedback ideas worth noting:

- Home Assistant 2025.10 plays a short beep instead of a spoken reply when every action took place in the satellite's own room ([HA Voice chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)).
- Willow displays the recognized text and the endpoint's output on screen ([How Willow Works](https://heywillow.io/how-willow-works/)).
- isair/jarvis centres on a "floating amber face" and offers "Pause Voice Listening", which stops room transcription while chat and dictation stay available. It also has a Task Centre that queues and tracks prompts ([isair README](https://github.com/isair/jarvis)).
- PanPenek's HUD shows an Arc Reactor indicator for listening, thinking, speaking and idle, next to a live tool-execution panel ([PanPenek README](https://github.com/PanPenek/JarvisAi)).

The notes found no primary documentation of how Open WebUI, Leon or OpenVoiceOS visually render listening, thinking and speaking.

## Users praise reach and privacy and complain about wake words, small models and security

Praise splits by project type. **OpenClaw is praised for actually doing things in the user's chat apps**: "OpenClaw is what Apple intelligence should have been" (518 points) and "OpenClaw is changing my life" (340 points, 513 comments), both from February 2026 ([HN 46893970](https://news.ycombinator.com/item?id=46893970); [HN 46931805](https://news.ycombinator.com/item?id=46931805)). Home Assistant's Voice PE sold out 23 minutes after its announcement ([HA Voice chapter 9](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)). OpenVoiceOS keeps goodwill as the local-first successor after Mycroft "collapsed" in 2023 from cloud dependence ([OVOS blog, 2025-05-20](https://blog.openvoiceos.org/posts/2025-05-20-ovos-and-mycroft-a-fork-that-wasnt-meant-to-be)). Open WebUI's 157.8k stars signal adoption, and one Hacker News commenter credits it with exposing model parameters that simpler UIs hide ([Open WebUI README](https://github.com/open-webui/open-webui); [HN thread via hn.svelte.dev](https://hn.svelte.dev/item/45798193)). Direct praise from Reddit was largely unreachable in this research, so the praise side is thinner than the complaints.

Complaints cluster into five failure classes, and JARVIS faces all of them:

1. **Wake words.** Users report "Okay Nabu" triggering Google devices, "Hey Jarvis" working only about half the time and "Hey Mycroft" producing many false positives. A 2026 ESPHome regression broke wake-word loading on Voice PE through a memory allocation failure ([HA community thread 911868](https://community.home-assistant.io/t/the-word-okay-in-the-default-wake-word-okay-nabu-should-probably-be-reconsidered/911868); [home-assistant/core issue 167989](https://github.com/home-assistant/core/issues/167989)).
2. **Small local models.** Open WebUI says models under about 30B "often produce malformed JSON". A 2026 Open Interpreter review says 7B models "produce too many errors for real tasks" (secondary source). Home Assistant users report wrong devices being toggled ([Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/); [DEV Community review 2026](https://dev.to/jovan_chan_9500711396d4e6/open-interpreter-review-2026-code-interpreter-offline-4g80); [HA community thread 983018](https://community.home-assistant.io/t/how-to-get-local-llm-working-correctly-with-assist/983018)).
3. **Windows reliability.** isair/jarvis's tracker shows a Windows app that freezes with a thinking beep (#89), all models failing to load on Windows with roughly 90 s replies (#549), and garbled Whisper transcripts (#495) ([isair/jarvis issues API](https://api.github.com/repos/isair/jarvis/issues?state=all&per_page=40&sort=comments)). Leon's Python Bridge 1.3.0 says "Windows is not supported for this version", and OpenVoiceOS has no native Windows installer ([Leon releases](https://github.com/leon-ai/leon/releases); [ovos-installer](https://github.com/ExploWare/ovos-installer)).
4. **Security** on the big platforms, covered above.
5. **Governance and churn.** Some users considered dropping Open WebUI over its 2025 licence change ([r/OpenWebUI mirror](https://redlib.hbubli.cc/r/OpenWebUI/comments/1kihdmc/new_license_has_started_discussion_of_pulling)). OpenClaw was caught in provider fights, including "Anthropic no longer allowing Claude Code subscriptions to use OpenClaw" (1,099 points, 2026-04-03) ([HN 47633396](https://news.ycombinator.com/item?id=47633396)). Any JARVIS bridge to a cloud subscription carries the same exposure.

## Licence cautions before borrowing code

**Open WebUI has not been OSI open source since v0.6.6 (2025-04-19).** Its custom licence forbids removing Open WebUI branding unless a deployment has 50 or fewer users in 30 days, has written permission or holds an enterprise licence. New contributors must sign a CLA ([Open WebUI licence docs](https://docs.openwebui.com/license/)). Borrow ideas from it, not code from after v0.6.5. Classic Open Interpreter (endolith fork) and the 01 voice project are **AGPL-3.0** ([endolith fork README](https://github.com/endolith/open-interpreter); [01 README](https://github.com/OpenInterpreter/01)). The Rust rewrite is Apache-2.0, and one secondary review says the licence moved from AGPL-3.0 ([PromptQuorum review](https://www.promptquorum.com/power-local-llm/open-interpreter-review)). isair/jarvis is "free for personal use" and requires contacting the author for commercial use. ethanplusai/jarvis is personal and non-commercial. Priler/jarvis is CC BY-NC-SA 4.0, and PanPenek/JarvisAi has no licence at all ([isair README](https://github.com/isair/jarvis); [ethanplusai README](https://github.com/ethanplusai/jarvis); [Priler README](https://github.com/Priler/jarvis); [PanPenek README](https://github.com/PanPenek/JarvisAi)). LiveKit Agents is Apache-2.0, but its turn-detector models, including the local `v1-mini`, fall under a separate LiveKit Model License ([LiveKit docs, turn detector](https://docs.livekit.io/agents/build/turns/turn-detector/)). The docs page does not state Smart Turn's model licence. Microsoft OmniParser is CC-BY-4.0 ([GitHub API repo query](https://api.github.com/search/repositories?q=repo:CursorTouch/Windows-MCP+repo:CursorTouch/Windows-Use+repo:OpenInterpreter/open-interpreter+repo:simular-ai/Agent-S+repo:bytebot-ai/bytebot+repo:microsoft/OmniParser)). The actively maintained Piper repository is named `piper1-gpl` ([GitHub API, piper1-gpl](https://api.github.com/repos/OHF-Voice/piper1-gpl/releases)). JARVIS should confirm which Piper package it pins and what licence that package carries. The clean permissive sources are Pipecat (BSD-2-Clause), Leon, OpenClaw, Hermes Agent, UFO and Windows-MCP (MIT).

## What JARVIS should take

Each item below names the source pattern and the design task it becomes. Items marked "decision needed" involve real tradeoffs. Under the project rules, those go to the user first and get logged in docs/DECISIONS.md.

### Tool orchestration architecture

**Ordered, tiered router config (OVOS `intents.pipeline`, HA `prefer_local_intents`).** Replace the implicit ordering of fast paths with an explicit list such as `router.pipeline: [exact_phrase, arithmetic, template_high, template_fuzzy, agent]`, where each stage returns match, partial or none with a confidence. Time-bound every stage and give each its own worker, after ovos-core 3.7.0's bounded match calls. That way a slow matcher can never stall the turn ([OVOS pipelines overview](https://openvoiceos.github.io/ovos-technical-manual/pipelines_overview/); [ovos-core releases](https://github.com/OpenVoiceOS/ovos-core/releases)).

**Runtime template matching with `{slot}` lists and an LRU cache (HA hassil templates, 128-entry `IntentCache`).** Extend the exact-phrase fast path to templates such as "open {app}" and "set volume to {percent}", filled from the tool registry at runtime rather than compiled at build time. Willow's fixed MultiNet grammar is the example not to follow ([HA Voice chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/); [default_agent.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/conversation/default_agent.py); [Willow Local Command Support](https://heywillow.io/features/Local-Command-Support/)).

**One executor, one transcript (HA intents as `llm.IntentTool`, shared chat log).** Every fast-path hit should run through the same tool registry and policy gate as the LangGraph loop. It should then be written into the LangGraph message state as a synthetic tool call and result, so "now make it louder" works after a fast-path "set volume". Add a test that fails if any fast path calls a tool function directly ([HA LLM API docs](https://contributors.home-assistant.io/core/internals/llm-api/); [HA blog, 2025-09-11](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)).

**A `handled_by` field on every turn (HA `processed_locally` on `intent-end`).** Record which router stage handled the turn (exact_phrase, arithmetic, template, agent) in the audit log and the turn-end event. That makes fast-path coverage measurable ([HA developer docs, voice pipelines](https://contributors.home-assistant.io/core/internals/assist-pipelines/)).

**Staged tool-schema loading (Leon toolkit then tool then function, Open WebUI `ENABLE_TOOL_SEARCH`, HA per-request `async_get_tools`).** Give Hermes 3 8B only toolkit summaries plus a gated `load_toolkit` meta-tool. Inject full schemas for one toolkit at a time, and cap visible tools per turn at a configured number. The cap can only be lowered by config ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md); [Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/)).

**Guard node before the executor (Leon runtime guards, LiveKit `max_tool_steps`).** Add a LangGraph node between model output and the policy gate. It validates arguments against the typed schema, allows one repair retry for malformed JSON, rejects a call identical to one already made this turn, and enforces a per-turn step cap ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md); [livekit/agents releases](https://github.com/livekit/agents/releases)).

**Named graph states (UFO2 HostAgent and AppAgent FSMs).** Model the LangGraph loop as explicit named states (route, plan, guard, gate, await_confirmation, execute, observe, respond), not a free loop. Each state maps one-to-one to a UI state event ([UFO2 overview](https://microsoft.github.io/UFO/ufo2/overview)).

**Front and back model split (Pipecat `LLMWithBackend` delegate, isair fast router model). Decision needed.** Evaluate a small router or acknowledgement model next to Hermes 3 8B. The tradeoff is VRAM on a 4 GB GPU against faster first words, and isair's README shows small defaults such as `gemma4:e2b` ([pipecat releases](https://github.com/pipecat-ai/pipecat/releases); [isair README](https://github.com/isair/jarvis)).

**API first, UI fallback for desktop tools (UFO2 "Native APIs (preferred)").** For each app tool, prefer a COM or Python API and use UIA clicks only as the fallback. Record which path ran in the audit log ([UFO2 overview](https://microsoft.github.io/UFO/ufo2/overview)).

### Plugin model

**Worst-case defaults for unknown tools (HA `llm.ToolAnnotations`, Open WebUI MCP Apps).** When the MCP client registers a server's tools, read MCP annotations but assume `destructive=True` and `open_world=True` unless JARVIS's own config says otherwise. Every third-party MCP tool should start at a `confirm` risk floor and a `private` sensitivity label, and server-declared annotations may only tighten that, never loosen it ([HA LLM API docs](https://contributors.home-assistant.io/core/internals/llm-api/); [Open WebUI releases](https://github.com/open-webui/open-webui/releases)).

**Namespaced tool names (HA `domain__name` prefix).** Register MCP tools as `mcp__<server>__<tool>` so a server cannot shadow a built-in tool such as `open_app`. Reject collisions at registration ([HA LLM API docs](https://contributors.home-assistant.io/core/internals/llm-api/)).

**Pinned arguments (Pipecat `MCPClient(tools_arguments=...)`).** Let the policy config pin arguments the model cannot set, such as a filesystem root for an MCP file server. Strip any model-supplied value for a pinned key in the guard node ([pipecat releases](https://github.com/pipecat-ai/pipecat/releases)).

**Installed, enabled, available states (Leon).** Add an availability check to the tool registry. A tool whose `.env` secret or device is missing is hidden from the model and reported as "unavailable" in the UI, rather than failing at call time ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md)).

**Interruption and timeout fields on the tool signature (Pipecat `cancel_on_interruption`, `timeout_secs`, `is_final`, `cancellable_by_llm`).** Extend the typed tool definition with `cancel_on_interruption: bool` (default True), `timeout_secs`, and an optional progress callback. Long tools such as downloads or calls report progress and can be cancelled by voice ([Pipecat function calling](https://docs.pipecat.ai/guides/learn/function-calling)).

**Workflow skills as files above typed tools (Leon `SKILL.md`, Hermes agentskills.io, Open WebUI on-demand skills).** Allow `SKILL.md` workflows loaded on demand that can only call registered typed tools. A skill never adds code, so the gate still sees every action ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md); [Hermes README](https://github.com/NousResearch/hermes-agent)).

### Safety and confirmation

**Confirmation as a graph interrupt with a non-interruptible prompt (Leon clarification pauses, LiveKit `allow_interruptions=False`, Pipecat `interruptible` flag).** Implement `confirm` as a LangGraph interrupt node. It speaks the action summary in a non-interruptible utterance, so echo cannot cancel it, then waits for the next user turn ([LiveKit docs, turns](https://docs.livekit.io/agents/build/turns/); [pipecat releases](https://github.com/pipecat-ai/pipecat/releases)).

**Deny on timeout (Open WebUI 120-second auto-deny).** An unanswered confirmation becomes a denial after a fixed timeout and is logged as `timeout_denied` ([Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/)).

**Per-turn taint escalation (ethanplusai "refuse acting tools after untrusted content").** Once a turn has read untrusted content (a web page, file, clipboard or MCP result), escalate every remaining `safe` acting tool in that turn to `confirm`. That is a tightening, so it fits the rule that config only tightens ([ethanplusai README](https://github.com/ethanplusai/jarvis)).

**Gate coverage tests for every entry point (Open WebUI CVE-2026-45395 lesson).** Enumerate every path that can register, update, import or invoke a tool: the registry, the MCP client, skills and the fast paths. Assert in tests that each one passes through the gate ([SentinelOne CVE-2026-45395](https://www.sentinelone.com/vulnerability-database/cve-2026-45395/)).

**Per-target risk (HA garage-relay finding).** Allow risk to be raised per target, such as a specific app, path or contact, not only per tool, because a dangerous effect can hide behind a benign category ([home-generative-agent PR 901](https://github.com/goruck/home-generative-agent/pull/901)).

**Cause attribution in the audit log (HA 2026.11 Action history).** Each audit entry records what caused the action: utterance id, `handled_by`, taint state and confirmation outcome. This mirrors Home Assistant's "what caused it" column ([HA 2026.11 release notes](https://www.home-assistant.io/blog/2026/11/04/release-202611/)).

**Wrapping Windows-MCP if mounted.** If Windows-MCP is ever mounted, block its Registry, PowerShell and Process tools, start the rest at `confirm`, and set `ANONYMIZED_TELEMETRY=false` in the spawned server's environment ([Windows-MCP README](https://github.com/CursorTouch/Windows-MCP)).

**Speaker check before voice-confirmed actions (OVOS speaker verification). Decision needed.** Consider requiring an enrolled-voice match before a voice "yes" can satisfy a `confirm` prompt ([OVOS blog archive](https://blog.openvoiceos.org/archive)).

### Latency

**Sentence-chunked streaming into Piper (HA streaming TTS, Open WebUI sentence-by-sentence TTS).** Start Piper at the first sentence boundary of the Hermes stream, and measure time to first audio against the 0.56 s Home Assistant reference ([HA blog, 2025-09-11](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)).

**Smart Turn v3 on CPU after a short VAD pause (Pipecat `LocalSmartTurnAnalyzerV3`, `stop_secs` 0.2, 3.0 s hard stop).** Add the ONNX end-of-turn classifier after a short VAD pause instead of a long silence timeout, and check its licence first ([Pipecat smart-turn overview](https://docs.pipecat.ai/server/utilities/turn-detection/smart-turn-overview)).

**Per-stage latency breakdown (Pipecat `LatencyBreakdown.contributions`).** Emit VAD silence, turn completion, STT, LLM first token, first audio and tool time for every turn into the audit log and docs/benchmarks ([pipecat releases](https://github.com/pipecat-ai/pipecat/releases)).

**Keep the model warm (HA Ollama `keep_alive` -1, think off).** Pin `keep_alive` and disable any thinking mode on the voice path ([HA Ollama integration](https://www.home-assistant.io/integrations/ollama/)).

**Bias STT with known names (HA Speech-to-Phrase idea, Pipecat faster-whisper `hotwords` and `initial_prompt`).** Feed tool, app and contact names into faster-whisper's hotwords or initial prompt ([pipecat releases](https://github.com/pipecat-ai/pipecat/releases); [HA Voice chapter 9](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)).

**Post-turn memory work (Leon async post-turn maintenance).** Run ChromaDB writes and memory extraction only after TTS has started, or while idle ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md)).

**False-interruption recovery and honest history (LiveKit `false_interruption_timeout`, `resume_false_interruption`, spoken-part storage).** Require a minimum duration or word count before barge-in, resume speech after a false interruption, and truncate the stored assistant message to what was actually played ([LiveKit docs, turns](https://docs.livekit.io/agents/build/turns/); [livekit/agents releases](https://github.com/livekit/agents/releases)).

### UI states

**State contract from LiveKit plus JARVIS extensions.** Publish `initializing`, `idle`, `listening`, `thinking` and `speaking` on the event bus. Add `awaiting_confirmation`, `running_tool`, `paused` and `error`, plus user states `speaking`, `listening` and `away`. Any new UI subscribes to this contract only ([LiveKit docs, events](https://docs.livekit.io/agents/build/events/)).

**Sub-stage events with typed error codes (HA pipeline events).** Emit `wake_word-end`, `stt-vad-start`, `stt-vad-end`, `intent-progress` and `tts-start`. Use error codes such as `stt_no_text_recognized`, so the UI can tell "did not hear you" apart from "did not understand" ([HA developer docs, voice pipelines](https://contributors.home-assistant.io/core/internals/assist-pipelines/)).

**Show the transcript and the route (Willow STT display, HA `processed_locally`).** Show what JARVIS heard and which path handled it, so mishearing is caught before a confirm prompt ([How Willow Works](https://heywillow.io/how-willow-works/)).

**Earcon instead of "Done" (HA 2025.10 non-verbal confirmations).** When a fast-path action has a visible effect on screen, play a short chime instead of speaking ([HA Voice chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)).

**Pause listening, keep typing (isair "Pause Voice Listening", Task Centre).** Provide a mic-off control that closes the capture stream while text input stays live. Add a task list for queued and background tool runs ([isair README](https://github.com/isair/jarvis)).

**Live tool feed as the visible audit log (PanPenek tool execution panel).** Render the audit log stream as the activity view, with decision, risk and cause per row ([PanPenek README](https://github.com/PanPenek/JarvisAi)).

## Where JARVIS can do better

**Confirmation on by default, enforced in code.** Every surveyed system either makes approval opt-in (Open WebUI, Open Interpreter's Python line), leaves it to prompts or "guidelines" (Windows-MCP), or has none in the voice path (Home Assistant, isair, PanPenek) ([Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/); [Windows-MCP README](https://github.com/CursorTouch/Windows-MCP); [HA exposing entities](https://www.home-assistant.io/voice_control/voice_remote_expose_devices/)). The design task: publish JARVIS's risk-floor table and gate behaviour as a documented contract with tests. That includes the rule that no config, MCP annotation or skill can lower a floor.

**Privacy-label routing that nobody else has.** No surveyed project documents routing by sensitivity label. Leon's context files include browser and activity data, and Open WebUI's memory is protected only by feature-level RBAC ([Leon ARCHITECTURE.md](https://raw.githubusercontent.com/leon-ai/leon/develop/core/context/ARCHITECTURE.md); [Open WebUI Memory docs](https://docs.openwebui.com/features/chat-conversations/memory/)). The design task: carry the sensitivity label on every tool result and memory record through the LangGraph state. The gate then blocks any cloud-bound call, such as the Claude Code bridge or a remote MCP server, whose inputs include a `private` value. That turns ethanplusai's per-turn taint into data-flow labels.

**Memory that the gate guards and the user can read.** Open WebUI lets the model write memory with no risk classification. JARVIS can make `add_memory` and `update_memory` gated tools with a sensitivity label. It can keep Open WebUI's `user` and `context` types with character budgets sized for an 8B context, and mirror ChromaDB contents into a human-editable file in `%LOCALAPPDATA%\Jarvis`, in the style of Leon's `OWNER.md` and ethanplusai's one-fact-per-file folder ([Open WebUI Memory docs](https://docs.openwebui.com/features/chat-conversations/memory/); [ethanplusai README](https://github.com/ethanplusai/jarvis)). The bigger projects favour memory users can inspect over opaque vectors. A ChromaDB index paired with a readable source of truth gets both.

**Cancellable everything.** Home Assistant's delayed commands "cannot be canceled or modified" ([HA Voice chapter 7](https://www.home-assistant.io/blog/2024/06/26/voice-chapter-7/)). The design task: give every scheduled or background tool run an id that "stop" or "cancel that" can reach in any state, including `awaiting_confirmation` and `running_tool`. Log the cancellation in the audit trail.

**Plugins that never run in the JARVIS process.** Open WebUI's in-process `exec()` of tools turned authorization gaps into code execution ([Open WebUI plugin overview](https://docs.openwebui.com/features/extensibility/plugin/); [SentinelOne CVE-2026-45395](https://www.sentinelone.com/vulnerability-database/cve-2026-45395/)). ClawHub showed that marketplaces spread malware ([HN 46898615](https://news.ycombinator.com/item?id=46898615)). The design tasks: keep third-party code out of process as MCP subprocesses, launched with a scrubbed environment in the style of ethanplusai stripping `ANTHROPIC_*` variables ([ethanplusai README](https://github.com/ethanplusai/jarvis)). Make installing any plugin or MCP server a `blocked`-by-default action that the user enables explicitly.

**Small-model reliability measured, not assumed.** Every reference project recommends 12B to 30B models for tool calling, and none publishes a malformed-call rate. The design task: log schema-validation failures, repairs and retries per tool in the guard node, and track them in docs/benchmarks. Then the size of the "Hermes 3 8B tax" is a number, and the router can move high-failure intents to the deterministic path ([Open WebUI Tools docs](https://docs.openwebui.com/features/extensibility/plugin/tools/)).

**Latency published on the actual hardware.** The notes found no official end-to-end figure for Home Assistant's Voice PE and no official LiveKit voice-to-voice benchmark. Willow's 500 ms is a 2023 vendor claim ([HA blog, Assist category](https://www.home-assistant.io/blog/categories/assist/); [heywillow.io](https://heywillow.io/)). JARVIS can publish per-stage percentiles from its own RTX 3050 4 GB laptop on every release. It can also be honest that Hermes 3 8B puts voice-to-voice above the roughly 1.2 s anecdotal 8B figure unless streaming and fast paths hide it.

**Windows as a first-class target, with failures named.** isair/jarvis is "developed primarily on macOS". Leon's Python bridge dropped Windows, OpenVoiceOS has no native installer, and Pipecat and LiveKit document no Windows testing ([isair README](https://github.com/isair/jarvis); [Leon releases](https://github.com/leon-ai/leon/releases); [ovos-installer](https://github.com/ExploWare/ovos-installer); [pipecat repo README](https://github.com/pipecat-ai/pipecat)). isair's tracker shows the cost: model-load failures and freezes on Windows (#89, #549). The design task: a startup health check that verifies each model loads and reports a named state for each component. isair's own proposal for this, PR #134, was closed ([isair/jarvis issues API](https://api.github.com/repos/isair/jarvis/issues?state=all&per_page=40&sort=comments)). Add docs/RISKS.md entries for the gaps that remain unsolved:

- no acoustic echo cancellation on laptop speakers;
- wake-word false accepts;
- UIA tools competing with the user for the real cursor, which UFO2's nested desktop avoids and Windows-MCP calls only "best-effort" ([UFO2 overview](https://microsoft.github.io/UFO/ufo2/overview); [Windows-MCP README](https://github.com/CursorTouch/Windows-MCP)).

**A documented visual state contract.** The notes found no primary documentation of how Open WebUI, Leon or OpenVoiceOS render listening, thinking and speaking. Home Assistant's own Voice PE state mapping could not be fetched ([Open WebUI voice and audio docs](https://docs.openwebui.com/ecosystem/computer/ai/voice-and-audio); [OVOS GUI service](https://openvoiceos.github.io/ovos-technical-manual/104-gui_service/)). JARVIS can write its state contract down before building the new UI: every state, the event that enters and leaves it, the visual and earcon for each, and an `awaiting_confirmation` view that shows the action, its risk floor, its target and why it was triggered. Any future surface binds only to 127.0.0.1, unlike `ovos-gui`'s default `0.0.0.0` bind ([OVOS GUI service](https://openvoiceos.github.io/ovos-technical-manual/104-gui_service/)).
